## Proposed runtime behavior

1. **Keep T1–T5 trigger thresholds, inference budgets and advisory authority unchanged.** At the existing safe `turn_end` boundary, construct a separate Worker-facing directive in `src/index.ts` from the trigger, the exact ineffective operation and bounded current evidence. Do not pass the supervisor's `issue/evidence/next_action` fields through as the entire Worker prompt. Preserve those fields for the visible diagnosis and audit record.
2. **Lead with an imperative stop rule and one alternate action.** For a repeated inspection, name the tool and arguments, say that repeated identical results add no evidence, and instruct the Worker not to call it again until a saved change or new relevant fact exists. Direct the Worker to one different read tied to the task or latest failed diagnostic. If no grounded alternate target is available, direct it to report the blocker instead of guessing. For a repeated no-op mutation, name decisive fields such as `dry_run:true`, `created:false`, `saved:false`, or `changes:[]`; a preview is never presented as a repair. Do not tell the Worker merely to “inspect the structure” when the repeated call already does that.
3. **Add a repair/verification exit condition.** After the alternate read, the Worker should make one focused persisted repair at a time, inspect the saved artifact or receipt, and report remaining uncertainty. An existing resource must be inspected and edited in place; the directive must never tell the Worker to recreate or overwrite it based solely on a failed test label. A timed-out runtime capture is not described as a successful smoke check.
4. **Constrain model suggestions.** Keep the supervisor's compact diagnosis schema if possible, but update `src/prompt.ts` to request a different operation or an explicit stop condition. Before delivery, reject a `next_action` that restates the repeated operation or gives only a generic inspection request; use a deterministic loop directive instead. The deterministic stop rule must survive a model reply that is syntactically valid but weak. Ground all named paths in the task, a current receipt, or current host diagnostic; avoid benchmark-specific hardcoding.
5. **Correct contradictory receipt interpretation.** In `src/core.ts`, a `dry_run:true` or `saved:false` result stays non-progress even when its receipt says `updated`. A `saved:true`, `dry_run:false`, `receipt.status=updated` scene-save result must not be classified as `NO_CHANGE` solely because a provider filled opaque before/after fields with null placeholders. Characterize this provider behavior with golden fixtures before changing classification. Keep all existing trigger counts and thresholds; review any resulting trigger-event differences explicitly.
6. **Make host diagnostic repair text usable.** In `src/index.ts`, summarize current host failures as short `ID: observed mismatch` lines without stack traces, clearly label them diagnostic rather than protected gate results, and prioritize saved-state failures. Keep a bounded current-stage diagnostic summary available to an emergency intervention occurring during that repair continuation. Do not promote diagnostic PASS to VERIFIED or let the Worker edit protected tests. Retain the one-retry limit.
7. **Show the directive clearly.** Render the command and first action in the collapsed intervention card. Expanded detail should quote the exact Worker prompt once, with evidence and confidence below it and word-aware wrapping. The card should not repeat the same paragraph as both summary and quoted prompt.

Illustrative Worker continuation for the second T4 (wording to validate in tests):

> Pi Sitter intervention for Stage 04. Stop calling `godot_inspection_get_scene_tree` with `{}` now: its last three results were identical. The earlier host diagnostic reported that saved `main.tscn` lacked `Meteors` and its attached script; a later save may have changed that state. Read the saved scene and `scripts/main.gd` through a different read path, compare them with those failures, and make only a supported in-place repair. Verify the saved result. If the evidence is still unclear, stop and report the blocker. Do not recreate an existing scene or call the same scene-tree read again without new state.

This example is not a claim that those earlier failures remain current after the save. The implementation must label their snapshot age and avoid prescribing a specific repair from stale evidence.
